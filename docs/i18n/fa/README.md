hostcensus یک ابزار خط فرمان (CLI) پایتون برای فهرست‌برداری تکرارپذیر سرویس‌ها در شبکه‌هایی است که مدیریت می‌کنید. این ابزار مواردی را که دستگاه‌ها در دسترس قرار می‌دهند ثبت می‌کند، مشاهدات را در طول زمان مقایسه می‌کند و اسکریپت‌های ورود اطلاعات برای Kadupul تولید می‌کند. بک‌اند پیش‌فرض از سوکت‌های asyncio بدون نیاز به دسترسی root استفاده می‌کند؛ کشف اختیاری با Nmap نیز می‌تواند میزبان‌ها را فراتر از پورت‌های سرویس پیکربندی‌شده شناسایی کند.

## چرا hostcensus

یک گزارش مقطعی و یک‌باره از پورت‌ها مشخص نمی‌کند که آیا مشاهده بعدی واقعاً تغییر کرده یا صرفاً ناموفق بوده است. hostcensus وضعیت‌های صریح سرویس، کاوش‌های محدودشده، پروفایل‌های اسکن قابل استفاده مجدد و تاریخچه محلی را با هم ترکیب می‌کند. اپراتورها می‌توانند همان محدوده را دوباره اسکن کنند، خطاها را بررسی کنند و مشاهدات نامطمئن را از تغییرات تاییدشده تشخیص دهند.

- **شواهد سرویس:** شناسایی SSH، پیام‌های خوشامدگویی MySQL، هدرهای HTTP، مشاهدات گواهی TLS و کشف SNMP یا پرس‌وجوهای احرازهویت‌شده system-MIB.
- **محدوده تکرارپذیر:** پروفایل‌های نام‌گذاری‌شده TOML، استثناهای افزایشی، سرویس‌های قابل پیکربندی، سقف تعداد میزبان/کاوش و ورکرهای محدودشده.
- **بررسی پیش از ارسال ترافیک:** پیش‌بررسی (preflight) محلی اهداف، ابزارها، دسترسی به مسیر مقصد، شمای تاریخچه و بسته‌های TLS CA پیکربندی‌شده را اعتبارسنجی می‌کند.
- **تاریخچه فهرست موجودی:** اسنپ‌شات‌های تراکنشی SQLite تمام مشاهدات را نگه می‌دارند؛ مقایسه‌ها خطاهای اسکنر و وضعیت‌های نامشخص را قابل مشاهده نگه می‌دارند.
- **خروجی سازگار برای تبادل داده:** گزارش‌های ترمینال، JSON و CSV، اسنپ‌شات‌های فایلی نسخه‌دار و اسکریپت‌های ورود برای Kadupul.

CI نسخه‌های 3.12، 3.13 و 3.14 پایتون را روی Linux و macOS به همراه یک آزمایشگاه یکپارچه‌سازی کنترل‌شده با Compose پوشش می‌دهد. کد از type aliasهای مدرن، نتایج پیش‌بررسی دارای نوع، پروفایل‌های slotشده با آرگومان‌های کلیدواژه‌ای اجباری و پاک‌سازی ساختاریافته async استفاده می‌کند و در عین حال پشتیبانی از همان نسخه‌های زمان اجرا را حفظ می‌کند. برای قرارداد سازگاری SemVer و فرآیند انتشار GitHub به [Versioning and releases](../../../docs/releasing.md) مراجعه کنید. نشان انتشار به مصنوعات منتشرشده اشاره دارد، نه به این نسخه checkout: جدیدترین تگ منتشرشده در حال حاضر `v0.3.0` است، در حالی که این checkout از نسخه بسته `3.0.0` استفاده می‌کند. برای استفاده از ویژگی‌های فهرست‌برداری مستندشده در اینجا، از روی checkout نصب کنید.

با [نصب](#install) شروع کنید و سپس بخش [پروفایل‌ها و تاریخچه](#inventory-profiles-preflight-and-local-history) را بخوانید. برای جزئیات یکپارچه‌سازی، به بخش‌های [اثرانگشت سرویس‌ها](#fingerprints)، [مقایسه فایل‌ها](#inventory-diff) و [خروجی Kadupul](#kadupul-export) مراجعه کنید.

## نصب

پایتون 3.12 یا جدیدتر مورد نیاز است؛ ماتریس آزمایش‌شده شامل پایتون 3.12 تا 3.14 است. از این checkout، وابستگی‌های قفل‌شده زمان اجرا را نصب کنید:

```bash
uv sync --locked
uv run hostcensus --help
uv run hostcensus --version
uv run hostcensus preflight 127.0.0.1
uv run hostcensus scan 127.0.0.1 --services ssh -o loopback.json
```

برای کشف اختیاری میزبان با Nmap، فایل اجرایی Nmap را با استفاده از مدیر بسته سیستم‌عامل خود نصب کنید؛ هیچ بسته پایتون اضافه‌ای لازم نیست. خروجی XML مربوط به Nmap با defusedxml (یک وابستگی اصلی) تجزیه می‌شود، بنابراین از بسط موجودیت‌ها (entity expansion) جلوگیری می‌شود. hostcensus دستور `nmap` موجود در `PATH` را مستقیماً با فهرستی ثابت از آرگومان‌ها، مهلتی که متناسب با اندازه پیشوند افزایش می‌یابد و سقف خروجی 64 MiB اجرا می‌کند. برای بک‌اند پیش‌فرض نیازی به Nmap نیست.

## مهاجرت از netprobe

hostcensus نام جدید netprobe است که در نسخه 3.0.0 منتشر شده است. این پروژه هرگز با هیچ‌یک از دو نام در PyPI منتشر نشده بود، بنابراین نصب‌ها از طریق checkout یا انتشارهای GitHub انجام می‌شد. مخزن GitHub نام خود را حفظ می‌کند.

| قبلاً | اکنون | سازگاری |
| --- | --- | --- |
| توزیع `netprobe` | `hostcensus` | از روی checkout دوباره نصب کنید؛ بسته‌ای با نام قدیمی وجود ندارد. |
| دستور `netprobe` | `hostcensus` | دستور `netprobe` همچنان اجرا می‌شود و یک خط هشدار منسوخ شدن در stderr چاپ می‌کند. کدهای خروج و stdout بدون تغییر هستند. در نسخه اصلی بعدی حذف می‌شود. |
| متغیرهای محیطی `NETPROBE_*` | `HOSTCENSUS_*` | متغیر `NETPROBE_*` زمانی استفاده می‌شود که همتای `HOSTCENSUS_*` آن تنظیم نشده باشد و یک هشدار در stderr چاپ می‌کند که نام متغیرها را ذکر می‌کند اما هرگز مقدار آن‌ها را نمایش نمی‌دهد. وقتی هر دو تنظیم شده باشند، `HOSTCENSUS_*` اولویت دارد. در نسخه اصلی بعدی حذف می‌شود. |
| `import netprobe`، `python -m netprobe` | `import hostcensus`، `python -m hostcensus` | **تغییر ناسازگار (Breaking).** هیچ لایه سازگاری برای import نصب نمی‌شود؛ importها را به‌روزرسانی کنید. |
| تگ ایمیج Docker به نام `network-discovery:test` (فقط CI) و کاربر کانتینر `netprobe` | `hostcensus:test`، کاربر `hostcensus` | هیچ ایمیجی هرگز در رجیستری منتشر نشده بود. ایمیج را دوباره بسازید و از entrypoint مربوط به `hostcensus` استفاده کنید. |
| `netprobe.toml`، `netprobe-history.sqlite3` | `hostcensus.toml`، `hostcensus-history.sqlite3` | فایل موجود با نام پیش‌فرض قدیمی، مادامی که نام جدید وجود نداشته باشد، همراه با یک هشدار همچنان استفاده می‌شود. مسیرهای صریح `--config` و `--history` دست‌نخورده باقی می‌مانند. |
| گزارش‌ها و اسنپ‌شات‌ها با `"format": "netprobe-report"` یا `"netprobe-snapshot"` و فیلد `netprobe_version` | `hostcensus-report`، `hostcensus-snapshot`، `hostcensus_version` | دستورات `diff` و `export` همچنان فایل‌های نوشته‌شده با نام قدیمی را بارگذاری می‌کنند و JSON Schemaهای منتشرشده هر دو املا را می‌پذیرند. فایل‌های جدید از نام‌های جدید استفاده می‌کنند. پایگاه‌داده‌های تاریخچه SQLite بدون تغییر هستند و مانند قبل بارگذاری می‌شوند. |
| اسکریپت‌های Kadupul از `netprobe export` | اسکریپت‌ها از `hostcensus export` | اسکریپت‌های قدیمی همچنان کار می‌کنند و هنگام اجرا همچنان `NETPROBE_SNMP_*` را می‌خوانند. اسکریپت‌های جدید `HOSTCENSUS_SNMP_*` را می‌خوانند. |

## مثال سریع

اجرا از کانتینر آزمایشگر در آزمایشگاه یکپارچه‌سازی توضیح‌داده‌شده در بخش توسعه؛ خروجی خلاصه شده است:

```console
$ hostcensus scan 172.30.57.8/29 --services ssh,http,snmp --save-snapshot after.json
┃ IP Address   ┃ Hostname       ┃ SSH ┃ SNMP ┃ MySQL ┃ Open services  ┃ Status ┃
│ 172.30.57.10 │ hostcensus-it-s… │ ✅  │  ❌  │  ❌   │ ssh:22         │ UP     │
│              │                │     │      │       │ OpenSSH_10.0   │        │
│ 172.30.57.13 │ hostcensus-it-w… │ ❌  │  ❌  │  ❌   │ http:80        │ UP     │
│              │                │     │      │       │ nginx/1.28.3   │        │

$ hostcensus diff before.json after.json; echo "exit=$?"
Warning: targets differ: 172.30.57.10 vs 172.30.57.8/29
│ new host │ 172.30.57.13 │ http:80/tcp  │ hostcensus-it-web-1.hostcensus-it_lab   │
exit=3

$ hostcensus export after.json -o kadupul-import.sh --template 1
$ grep 57.13 kadupul-import.sh
add --description=hostcensus-it-web-1.hostcensus-it_lab --ip=172.30.57.13 --template=1 --version=0 --avail=ping --ping_method=tcp --ping_port=80 '--notes=hostcensus: http:80/tcp nginx/1.28.3'
```

## کدهای خروج

| دستور | 0 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| `scan` | مشاهدات/گزارش ثبت شد | شکست در پیش‌بررسی/بک‌اند، یا خطا در نوشتن تاریخچه یا گزارش/اسنپ‌شات | هدف، گزینه‌ها، پیکربندی یا محدودیت‌های نامعتبر | - | زمان `--deadline` به پایان رسید؛ گزارش ناقص نوشته شد، تاریخچه و اسنپ‌شات رد شدند |
| `preflight` | بررسی‌ها با موفقیت گذشتند | بررسی محلی ناموفق بود | هدف/پیکربندی نامعتبر یا مسیرهای مقصد متعارض | - | - |
| `profiles` | پروفایل‌های اعتبارسنجی‌شده فهرست شدند | - | پیکربندی یا انتخاب غیرقابل خواندن/نامعتبر | - | - |
| `history` | خلاصه‌ها فهرست شدند | تاریخچه مفقود، نامعتبر یا پشتیبانی‌نشده | گزینه‌های CLI نامعتبر | - | - |
| `compare` | مقایسه انجام شد، حتی زمانی که تغییرات وجود داشته باشند | تاریخچه غیرقابل خواندن، محدوده/ترتیب ناسازگار، یا خطای نوشتن | گزینه‌های CLI نامعتبر | - | - |
| `diff` | بدون تغییر | فایل `-o` قابل نوشتن نبود | ورودی مفقود، غیرقابل خواندن یا پشتیبانی‌نشده، یا اسکن ناقص بدون `--allow-partial` | تغییرات یافت شد، مشاهدات تاییدنشده، یا اسکن ناقص | - |
| `export` | اسکریپت نوشته شد | اسکریپت قابل نوشتن نبود | ورودی غیرقابل خواندن، اسکن ناقص بدون `--allow-partial`، یا داده‌هایی که نمی‌توان به‌صورت ایمن خروجی گرفت | - | - |

## ساختار ماژول‌ها

| ماژول | مسئولیت |
| --- | --- |
| `cli.py` | گزینه‌های خط فرمان، تفکیک پروفایل، پیش‌بررسی، اسکن و گزارش‌دهی |
| `scanner.py`، `probes.py` | بسط اهداف، ورکرهای محدودشده، کشف میزبان و مشاهدات سرویس |
| `config.py`، `profiles.py` | تعاریف سرویس و پروفایل‌های فهرست‌برداری اعتبارسنجی‌شده |
| `models.py`، `output.py` | انواع نتیجه و رندر خروجی ترمینال/JSON/CSV |
| `history.py`، `diff.py` | تاریخچه SQLite و مقایسه اسنپ‌شات‌های فایلی نسخه‌دار |
| `preflight.py` | بررسی‌های محلی و استعلام محدودشده نسخه Nmap |
| `export.py` | اسکریپت‌های ورود Kadupul اعتبارسنجی‌شده و نقل‌قول‌شده |

هر مشاهده سرویس، وضعیت خود را جدا از هویت اعلام‌شده ثبت می‌کند. عملیات خواندن و مهلت‌های زمانی محدود هستند؛ استثناهای کاوش در خطاهای میزبان باقی می‌مانند. تاریخچه SQLite از تراکنش‌ها، پاک‌سازی صریح اتصال و مسیرهای فقط‌خواندنی برای فهرست‌گیری و مقایسه استفاده می‌کند. اسرار SNMP فقط از طریق متغیرهای محیطی یا فایل‌های محرمانه وارد می‌شوند؛ تاریخچه فهرست موجودی تنظیمات غیرمحرمانه موثر را ذخیره می‌کند. برای خط لوله اسکن، محدودیت‌ها و مرزهای اعتماد آن به [Architecture](../../../docs/architecture.md) و برای استفاده مجاز به [SECURITY.md](../../../SECURITY.md#authorized-use) مراجعه کنید.


## نحوه استفاده

فقط شبکه‌هایی را اسکن کنید که خودتان مدیریت می‌کنید.

```bash
hostcensus scan 192.168.1.0/24              # table of alive hosts
hostcensus scan 192.168.1.1 -o results.json # JSON report
hostcensus scan 10.0.0.0/24 -o report.csv   # CSV report
hostcensus scan 10.0.0.0/24 -q -o out.json  # no table, file only
hostcensus scan 10.0.0.0/24 --format json | jq '.devices[]'  # JSON report on stdout
```

| گزینه | معنا |
| --- | --- |
| `NETWORK` | CIDR، نشانی IP یا نام میزبان؛ همراه با `--profile` اختیاری است. شناسه‌های محدوده IPv6 رد می‌شوند. |
| `-o, --output PATH` | نوشتن گزارش. قالب بر اساس پسوند تعیین می‌شود (`.json`، `.csv`)؛ سایر پسوندها به JSON برمی‌گردند. |
| `-f, --format json\|csv\|kadupul\|auto` | اجبار قالب گزارش. بدون `--output` اثری ندارد. پسوند `.sh` قالب `kadupul` را انتخاب می‌کند. |
| `-v, --verbose` | ثبت لاگ اشکال‌زدایی (debug). |
| `-q, --quiet` | پنهان کردن نتایج، پیشرفت و لاگ‌های اطلاع‌رسانی؛ هشدارها و خطاها همچنان در stderr نمایش داده می‌شوند. |
| `--backend asyncio\|nmap` | کشف میزبان. `asyncio` (پیش‌فرض) پورت‌های سرویس را مستقیماً کاوش می‌کند؛ `nmap` ابتدا یک پینگ‌اسکن nmap اجرا می‌کند و به فایل اجرایی `nmap` در `PATH` نیاز دارد. |
| `--timeout SECONDS` | زمان انتظار برای کاوش‌هایی که بودجه زمانی خودشان را تعیین نمی‌کنند (پیش‌فرض 1.0). کاوش‌های اتصال داخلی از 0.3 ثانیه استفاده می‌کنند مگر اینکه جدول سرویس `timeout` را تنظیم کرده باشد. |
| `--concurrency N` | تعداد کاوش‌های هم‌زمان در حال اجرا (پیش‌فرض 256). |
| `--deadline SECONDS` | توقف کل اسکن، از جمله جاروب nmap، پس از این مدت (پیش‌فرض 3600، حداکثر 604800؛ متغیر محیطی `HOSTCENSUS_DEADLINE`). میزبان‌هایی که به پایان رسیده‌اند با `"complete": false` در گزارش نوشته می‌شوند، هیچ تاریخچه یا اسنپ‌شاتی نوشته نمی‌شود و `scan` با کد 4 خارج می‌شود. |
| `--config PATH` | تعاریف سرویس TOML و تنظیمات اختیاری نام‌گذاری‌شده `[profiles]`. |
| `--profile NAME` | استفاده از یک پروفایل نام‌گذاری‌شده؛ در صورت حذف `--config` به‌طور پیش‌فرض از `hostcensus.toml` استفاده می‌کند. |
| `--exclude IP/CIDR` | افزودن یک استثنا؛ در صورت نیاز تکرار کنید. یک میزبان IPv4 مستثناشده، نشانی‌های IPv6 متصل به آن را نیز مستثنا می‌کند: نگاشت‌شده به IPv4 (`::ffff:a.b.c.d`)، NAT64 (`64:ff9b::/96`) و 6to4. اهداف و استثناهای نگاشت‌شده به IPv4 به‌عنوان همان نشانی‌های IPv4 که نشان می‌دهند در نظر گرفته می‌شوند. |
| `--max-hosts N` | محدودیت نشانی که پیش از اعمال استثناها بررسی می‌شود (پیش‌فرض و سقف سخت 65,536). |
| `--history PATH` | ثبت اسکن تکمیل‌شده در یک پایگاه‌داده تاریخچه SQLite اختیاری. |
| `--services NAMES` | فهرست جداشده با کاما از نام سرویس‌ها برای بررسی، به همان ترتیب (پیش‌فرض: همه). |
| `--ports SPEC` | فهرست جداشده با کاما از `NAME=PORT` (جابه‌جایی یک سرویس) یا `PORT` (افزودن یک بررسی ساده TCP با نام `tcp-PORT`). |
| `--snmp-community-file PATH` | فایلی حاوی community مربوط به SNMPv2c برای پرس‌وجوی system MIB. متغیر محیطی: `HOSTCENSUS_SNMP_COMMUNITY` (مقدار) یا `HOSTCENSUS_SNMP_COMMUNITY_FILE` (مسیر). |
| `--snmp-user` | کاربر SNMPv3. متغیر محیطی: `HOSTCENSUS_SNMP_USER`. |
| `--snmp-auth-protocol`, `--snmp-auth-key-file PATH` | `MD5`، `SHA` (پیش‌فرض)، `SHA224`، `SHA256`، `SHA384`، `SHA512` و فایلی حاوی عبارت عبور. متغیر محیطی: `HOSTCENSUS_SNMP_AUTH_PROTOCOL`، `HOSTCENSUS_SNMP_AUTH_KEY` یا `HOSTCENSUS_SNMP_AUTH_KEY_FILE`. |
| `--snmp-priv-protocol`, `--snmp-priv-key-file PATH` | `DES`، `AES` (پیش‌فرض)، `AES128`، `AES192`، `AES192C`، `AES256`، `AES256C` و فایلی حاوی عبارت عبور. متغیر محیطی: `HOSTCENSUS_SNMP_PRIV_PROTOCOL`، `HOSTCENSUS_SNMP_PRIV_KEY` یا `HOSTCENSUS_SNMP_PRIV_KEY_FILE`. |
| `--save-snapshot PATH` | همچنین یک اسنپ‌شات نسخه‌دار برای `hostcensus diff` می‌نویسد. |
| `--tls-ca-file PATH` | گواهی‌های HTTPS را به جای مخزن سیستم، با این بسته PEM اعتبارسنجی می‌کند. متغیر محیطی: `HOSTCENSUS_TLS_CA_FILE`. |

به‌طور پیش‌فرض هر میزبان از نظر SSH (TCP 22)، SNMP (UDP 161)، MySQL (TCP 3306)، HTTP (TCP 80) و HTTPS (TCP 443) بررسی می‌شود. پورت‌های TCP با یک اتصال کامل آزمایش می‌شوند. SNMP با یک درخواست کشف موتور SNMPv3 آزمایش می‌شود که هر عامل SNMPv3 موظف است بدون احرازهویت به آن پاسخ دهد؛ عامل‌هایی که فقط با v1/v2c صحبت می‌کنند توسط این کاوش شناسایی نمی‌شوند. با بک‌اند asyncio، میزبانی زنده محسوب می‌شود که هر کاوشی پاسخی دریافت کند، از جمله رد اتصال (refused connection)؛ بنابراین میزبانی که تمام کاوش‌ها را دور می‌اندازد دارای `alive=false` و خطای "Host is down" خواهد بود که این امر خاموش بودن فیزیکی آن را اثبات نمی‌کند. با `--backend nmap`، خود nmap تصمیم می‌گیرد کدام میزبان‌ها زنده هستند (با دسترسی root از طریق ICMP و در غیر این صورت TCP 80/443).

### اثرانگشت سرویس‌ها

هر سرویس باز بر اساس داده‌ای که پیش از هرگونه ورود (login) ارسال می‌کند، اثرانگشت‌برداری می‌شود. هیچ چیز احراز هویت انجام نمی‌دهد به جز پرس‌وجوی SNMP، آن هم فقط زمانی که اطلاعات احراز هویت را ارائه دهید.

| کاوش | چه چیزی می‌خواند | `version` | کلیدهای `details` |
| --- | --- | --- | --- |
| `ssh` | خط شناسایی RFC 4253 | نرم‌افزار، مثلاً `OpenSSH_10.0` | `protocol`، `software`، `comments` |
| `mysql` | دست‌دهی اولیه MySQL/MariaDB | نسخه سرور | `server_version`، `flavor`، `auth_plugin` یا `error_code`/`error` |
| `http` | پاسخ `HEAD /` | هدر `Server` | `status`، `server` |
| `https` | دست‌دهی TLS، گواهی، `HEAD /` | هدر `Server` | `tls_version`، `cert_verified`، `cert_verify_error`، `cert_subject`، `cert_issuer`، `cert_sans`، `cert_not_before`، `cert_not_after` (فرمت UTC ISO 8601)، `cert_self_signed`، `status`، `server` |
| `snmp` | کشف SNMPv3؛ با اطلاعات احراز هویت، GET برای sysDescr، sysObjectID، sysName | sysDescr | `engine_id`؛ با اطلاعات احراز هویت: `snmp_version`، `sys_descr`، `sys_object_id`، `sys_name` یا `snmp_error` |

یک هدف از نوع نام میزبان برای هر میزبان یک بار تفکیک (resolve) می‌شود و هر کاوش به همان نشانی متصل می‌شود که در نتایج به عنوان `address` ثبت می‌گردد؛ نام میزبان فقط برای TLS SNI، اعتبارسنجی گواهی و هدر `Host` در HTTP استفاده می‌شود. نامی که تفکیک نشود وضعیت‌های `unknown` و خطای `Cannot resolve` ایجاد می‌کند. نام‌های DNS معکوس فقط زمانی نگه داشته می‌شوند که شامل کاراکترهای مجاز نام میزبان باشند و حداکثر 16 استعلام به طور هم‌زمان اجرا می‌شود. HTTPS از اعتبارسنجی گواهی و نام میزبان در برابر مخزن سیستم یا `--tls-ca-file` استفاده می‌کند. مخزن اعتماد یک بار برای اسکن بارگذاری می‌شود و برای هر کاوش HTTPS دوباره استفاده می‌گردد. اتصال TCP و دست‌دهی TLS به‌طور جداگانه زمان‌بندی می‌شوند، بنابراین پورتی که اتصال را می‌پذیرد اما در دست‌دهی متوقف می‌شود، به عنوان `open` با `tls_error` ثبت می‌شود، نه `filtered`. اگر اعتبارسنجی شکست بخورد، نتیجه `cert_verified: false` و `cert_verify_error` را ثبت می‌کند؛ با تنظیمات ضعیف‌تر دوباره تلاش نمی‌کند و درخواست HTTP ارسال نمی‌کند. جزئیات گواهی و هدرهای HTTP فقط پس از موفقیت در اعتبارسنجی جمع‌آوری می‌شوند. برای سرویس‌های دارای CA خصوصی، بسته CA صحیح را ارائه دهید. گزارش‌های قدیمی‌تر ممکن است حاوی `cert_read_unverified` باشند که کاوش‌های فعلی دیگر تولید نمی‌کنند.

اسرار SNMP فقط از متغیرهای محیطی یا از فایل‌ها (`--snmp-*-file` یا متغیر متناظر `HOSTCENSUS_SNMP_*_FILE`) خوانده می‌شوند و هرگز از مقادیر خط فرمان که سایر کاربران محلی می‌توانند در فهرست پردازش‌ها ببینند خوانده نمی‌شوند. گزینه‌های `--snmp-community`، `--snmp-auth-key` و `--snmp-priv-key` همراه با مقدار، با کد 2 خارج می‌شوند و جایگزین مناسب را معرفی می‌کنند. فایل محرمانه باید UTF-8 غیرخالی و حداکثر 4096 بایت باشد؛ یک خط جدید پایانی نادیده گرفته می‌شود و تنظیم هم‌زمان یک متغیر و یک فایل برای یک راز واحد خطا محسوب می‌شود. خطاها نام فایل را ذکر می‌کنند اما هرگز محتوای آن را چاپ نمی‌کنند. گزارش‌های اسکن و تاریخچه به‌طور عمدی مقادیر احراز هویت را شامل نمی‌شوند. ابزار خروجی‌گیری گزینه جداگانه و صریح `--include-credentials` دارد که در ادامه توضیح داده شده است. یک community باعث انتخاب SNMPv2c می‌شود؛ یک کاربر باعث انتخاب SNMPv3 می‌شود که در صورت دادن کلید احراز هویت با احراز هویت و در صورت دادن هر دو کلید با محرمانگی خواهد بود (`snmp_security_level` نوع آن را ثبت می‌کند). hostcensus با کد خروج 2 از ترکیب کردن یک community با کاربر v3، استفاده از کلید محرمانگی بدون کلید احراز هویت یا استفاده از کلیدها بدون کاربر خودداری می‌کند و هرگز یک پرس‌وجوی ناموفق v3 را با v2c یا سطح امنیتی پایین‌تر دوباره امتحان نمی‌کند. عامل‌هایی که فقط v1/v2c صحبت می‌کنند، کشف بدون احراز هویت v3 را نادیده می‌گیرند، بنابراین فقط زمانی به عنوان open نمایش داده می‌شوند که یک community ارائه شود.

متن بنرها به کاراکترهای قابل چاپ کاهش یافته و پیش از ذخیره یا نمایش به 256 کاراکتر محدود می‌شود. عملیات خواندن نیز محدود هستند: 4 KiB برای هر خط، 4 KiB برای پیام خوشامدگویی MySQL و 16 KiB برای هدرهای HTTP. یک شناسه موتور SNMP بزرگ‌تر از 32 اوکتت پیش از ذخیره کوتاه می‌شود. HTTP و HTTPS هدر Host را برای نشانی IPv6 در براکت و در صورتی که پورت 80 یا 443 نباشد همراه با شماره پورت ارسال می‌کنند. سلول‌های CSV که با نشانگر فرمول صفحه گسترده شروع می‌شوند پیشوند می‌گیرند تا سلول به صورت متن باقی بماند.

### محدودیت‌ها

یک اجرا حداکثر 65,536 نشانی، 64 سرویس و 524,288 کاوش (تعداد میزبان‌ها ضرب در سرویس‌ها) را می‌پذیرد؛ درخواست‌های بزرگ‌تر پیش از ارسال هر ترافیکی با کد 2 خارج می‌شوند. `--concurrency` به 4096 سوکت محدود شده است. هر کاوش یک مهلت سخت برابر با چهار برابر بودجه زمانی خودش دارد. کاوش‌های اتصال (`tcp`، `ssh`، `mysql`، `http`) از 0.3 ثانیه استفاده می‌کنند مگر اینکه آن سرویس `timeout` را تنظیم کرده باشد. SNMP و HTTPS وقتی زمانی برایشان تنظیم نشده باشد از `--timeout` (پیش‌فرض 1.0) استفاده می‌کنند. کاوشی که به مهلت سخت برسد به‌صورت `unknown` با عبارت "probe timed out" در `errors` گزارش می‌شود. خطاهای سوکت محلی (مثلاً تمام شدن توصیف‌گرهای فایل) نیز به عنوان `unknown` همراه با ثبت خطا گزارش می‌شوند؛ آن‌ها هرگز به عنوان پورت فیلترشده یا میزبان خاموش شمرده نمی‌شوند. پیش از کاوش، hostcensus محدودیت نرم فایل‌های باز را به سمت محدودیت سخت بالا می‌برد تا `--concurrency` به علاوه 64 توصیف‌گر را جا دهد؛ وقتی نتواند، بررسی پیش‌بررسی `open files` شکست می‌خورد و `scan` پیش از ارسال ترافیک با کد 1 خارج می‌شود. کشف با Nmap از مهلت میزبان 30 ثانیه‌ای استفاده می‌کند. یک پیشوند در قالب CIDR به nmap داده می‌شود و وقتی nmap تعداد نشانی کمتری نسبت به آنچه دریافت کرده گزارش دهد (مثلاً نامی که نتواند تفکیک کند)، جاروب به جای علامت‌گذاری میزبان‌ها به عنوان خاموش، با کد خروج 1 شکست می‌خورد. یک هدف نام میزبان یک بار تفکیک شده و همان نشانی به nmap داده می‌شود تا کشف و کاوش‌ها به یک ماشین واحد برسند. یک پیشوند کامل در قالب یک پردازش nmap اجرا می‌شود که مهلت زیرپردازش آن به ازای هر 256 نشانی 35 ثانیه (رو به بالا گرد شده) است. جاروب‌های دارای استثنا از دسته‌های 256 میزبانی و مهلت 35 ثانیه‌ای برای هر دسته استفاده می‌کنند. ایجاد ورکرها مستقل از اندازه بازه محدود شده است. DNS معکوس و تفکیک نام میزبان مهلت جداگانه دو ثانیه‌ای دارند؛ یک فراخوانی تفکیک‌کننده که هرگز برنمی‌گردد در نخ (thread) خودش رها می‌شود تا نتواند hostcensus را فراتر از این محدودیت‌ها فعال نگه دارد. حداکثر 16 استعلام به طور هم‌زمان اجرا می‌شوند و یک فراخوانی رهاشده تا زمان بازگشت، جایگاه خود را حفظ می‌کند تا تعداد نخ‌های گیرکرده محدود بماند؛ اگر همه 16 مورد گیر کنند، استعلام‌های بعدی خارج از مهلت دو ثانیه‌ای (که پس از آزاد شدن جایگاه شروع می‌شود) در صف قرار می‌گیرند تا زمانی که `--deadline` اسکن را متوقف کند. استفاده از `NetworkScanner` به عنوان کتابخانه بدون `deadline` می‌تواند به‌طور نامحدود منتظر چنین جایگاهی بماند. `--deadline` (پیش‌فرض یک ساعت) کل اجرا را علاوه بر این موارد محدود می‌کند.

### پیکربندی سرویس‌ها

سرویس‌ها را می‌توان با یک فایل TOML تغییر داد:

```toml
[services.ssh]          # same name as a built-in: replaces it
port = 2222
timeout = 0.5

[services.admin-ui]     # a new service, probed like HTTPS
port = 8443
probe = "https"
```

مقدار `probe` یکی از `tcp`، `ssh`، `mysql`، `http`، `https` یا `snmp` است و وقتی نام سرویس خودش یک کاوش باشد به‌طور پیش‌فرض همان است و در غیر این صورت `tcp` می‌شود. فقط `snmp` از UDP استفاده می‌کند. نام سرویس‌ها از حروف کوچک، ارقام، `-` و `_` تشکیل می‌شود. دو سرویس نمی‌توانند پورت و پروتکل مشترک داشته باشند؛ تاریخچه برای آن جفت یک وضعیت ثبت می‌کند. `timeout` اختیاری، بر حسب ثانیه و حداقل 0.05 است. کاوش‌های نوع اتصال (`tcp`، `ssh`، `mysql`، `http`) به‌طور پیش‌فرض 0.3 ثانیه هستند. `snmp` و `https` وقتی سرویس `timeout` را تنظیم نکند از `--timeout` اسکن استفاده می‌کنند. `--timeout` جایگزین بودجه زمانی‌ای که سرویس از قبل دارد نمی‌شود.

گزارش‌های JSON اسناد نسخه‌داری هستند (`"format": "hostcensus-report"`، `"version": 1`) که هدف، سرویس‌های کاوش‌شده و تنظیمات را در کنار `devices` ثبت می‌کنند؛ `--format json` بدون `-o` گزارش را به جای جدول در stdout می‌نویسد. هر خروجی JSON دارای یک شمای منتشرشده است؛ به [JSON output](../../../docs/json-output.md) مراجعه کنید. دستگاه‌ها فیلدهای اصلی `ip`، `alive`، `ssh`، `snmp`، `mysql`، `hostname` و `errors` را نگه می‌دارند و یک فهرست `services` شامل `name`، `port`، `protocol`، `state` (`open`، `closed`، `filtered` یا `unknown` در صورت شکست محلی کاوش یا رسیدن به مهلت)، `version` و `details` هر کاوش را اضافه می‌کنند. خروجی CSV ستون‌های انتهایی `services` و `versions` را برای سرویس‌های باز دریافت می‌کند. مقادیر بولی `ssh`، `snmp` و `mysql` از سرویس‌هایی با دقیقاً همین نام‌ها پیروی می‌کنند.

## پروفایل‌های فهرست‌برداری، پیش‌بررسی و تاریخچه محلی

پروفایل‌های نام‌گذاری‌شده یک فایل TOML مشترک با تعاریف موجود `[services]` دارند. فایل [hostcensus.example.toml](../../../hostcensus.example.toml) را در `hostcensus.toml` کپی کنید و شبکه‌هایی را که مدیریت می‌کنید تنظیم کنید:

```toml
[profiles.office]
network = "192.168.1.0/24"
exclusions = ["192.168.1.1"]
services = "ssh,http,https,mysql"
concurrency = 32
timeout = 1.0
max_hosts = 256
backend = "asyncio"
```

```bash
hostcensus profiles --config hostcensus.toml
hostcensus preflight --profile office --config hostcensus.toml
hostcensus scan --profile office --config hostcensus.toml -o report.json
```

دستور `preflight` گزینه‌ها و پروفایل‌ها را دقیقاً مانند `scan` تفکیک می‌کند، از جمله `--concurrency` برای بررسی فایل‌های باز، بنابراین عبور موفق از پیش‌بررسی به این معناست که `scan` با همان نقشه شروع خواهد شد.

پروفایل‌ها فیلدهای `network`، `exclusions`، `services`، `ports`، `backend`، `timeout`، `concurrency` و `max_hosts` را می‌پذیرند. `services` و `ports` از همان نحو فهرست جداشده با کاما استفاده می‌کنند. گزینه‌های صریح CLI تنظیمات پروفایل را بازنویسی می‌کنند؛ تکرار `--exclude` به استثناهای پروفایل اضافه می‌شود. یک شبکه صریح همراه با `--profile` باید در محدوده IP/CIDR آن پروفایل قرار داشته باشد. نام‌های میزبان همچنان برای اسکن‌های مستقیم پشتیبانی می‌شوند، اما نمی‌توانند با استثناهای IP ترکیب شوند. محدودیت‌های میزبان پیش از استثناها اعمال می‌شوند؛ سقف کل کاوش‌ها همچنان پس از آن اعمال می‌گردد. میزبان‌های مستثناشده هم از بررسی‌های سرویس و هم از کشف اختیاری Nmap حذف می‌شوند.

هر اسکن پیش از ارسال ترافیک به اهداف، بررسی‌های محلی پیش‌بررسی را انجام می‌دهد: محدودیت‌های هدف/کاوش، دسترسی مقصد، در دسترس بودن فایل اجرایی/پوشاننده (wrapper) اختیاری Nmap، شمای تاریخچه و بسته TLS CA پیکربندی‌شده. `preflight` خروجی JSON گزارش می‌دهد و اهداف را اسکن نمی‌کند یا پایگاه‌داده تاریخچه نمی‌سازد. این دستور به‌طور موقت یک فایل هم‌جوار می‌نویسد تا دسترسی مقصد را بدون تغییر محتوای موجود آزمایش کند. بک‌اند پیش‌فرض asyncio همچنان نه به Nmap نیاز دارد و نه به دسترسی root. مسیرهای مقصد باید از یکدیگر و از پیکربندی ورودی متمایز باشند، از جمله پیوندهای سخت (hard links)؛ پیوندهای نمادین (symlinks) در مقصد رد می‌شوند. بررسی‌های ناموفق کد 1 و محدوده/پیکربندی نامعتبر کد 2 برمی‌گردانند.

نوشتن گزارش و خروجی مستلزم پشتیبانی از `O_NOFOLLOW` است. روی پلتفرم‌های فاقد این قابلیت، از جمله Windows، این نوشتن‌ها بدون باز کردن یا کوتاه کردن (truncate) فایل مقصد شکست می‌خورند. گزارش‌ها و اسکریپت‌های خروجی جدید فقط برای مالک قابل دسترسی هستند (حالت 0600)؛ جایگزینی یک فایل موجود دسترسی‌های آن را حفظ می‌کند. نوشتن در یک لوله نام‌گذاری‌شده (named pipe) بدون خواننده بلافاصله به جای انتظار شکست می‌خورد. یک پایگاه‌داده `--history` جدید نیز فقط برای مالک ساخته می‌شود؛ پایگاه‌داده موجود حالت خود را حفظ می‌کند. پیام‌های لاگ همیشه به stderr می‌روند تا stdout فقط نتایج را حمل کند. خروجی‌های حاوی اطلاعات احراز هویت همیشه حالت 0600 را اجبار می‌کنند.

تاریخچه اختیاری است و مکمل اسنپ‌شات‌های JSON موجود و دستور `diff` است:

```bash
mkdir -p output
hostcensus scan --profile office --history output/inventory.sqlite3
# Repeat later with the same targets and service selection.
hostcensus scan --profile office --history output/inventory.sqlite3
hostcensus history --history output/inventory.sqlite3 --limit 20
hostcensus compare 1 2 --history output/inventory.sqlite3
hostcensus compare 1 2 --history output/inventory.sqlite3 -o output/changes.json
```

از شناسه‌های خروجی `history` استفاده کنید؛ مثال فرض می‌کند پایگاه‌داده جدید است. اسنپ‌شات‌ها به‌صورت تراکنشی همراه با زمان‌های شروع/پایان UTC، نسخه بسته، تنظیمات موثر غیرمحرمانه، خلاصه‌ها و تمام مشاهدات میزبان/سرویس، از جمله خطاهای هر میزبان ذخیره می‌شوند. مشاهدات ناقص میزبان نگه داشته می‌شوند. اجراهای لغوشده ذخیره نمی‌شوند. قراردادهای موجود گزارش، اسنپ‌شات، خروجی‌گیری و کد خروج اسکن حفظ می‌شوند.

`history` خلاصه‌های JSON را بدون خواندن تمام بارهای داده دستگاه‌های تاریخی فهرست می‌کند. `compare` دو اسکن ذخیره‌شده را می‌خواند، نیازمند هویت هدف و پورت‌های انتخاب‌شده یکسان است و تغییرات پاسخ‌دهی، وضعیت و وضعیت پورت‌ها را گزارش می‌دهد. شناسه اسکن قدیمی‌تر باید پیش از شناسه جدیدتر باشد. وقتی هر دو اسکن `timeout` یا `backend` را ثبت کرده باشند و آن مقادیر متفاوت باشند، گزارش یک هشدار فهرست می‌کند و همچنان مشاهدات را مقایسه می‌کند. زمان انتظار متفاوت می‌تواند باعث شود یک پورت فیلترشده، باز به نظر برسد. خطاهای اسکنر و مشاهدات پورت نامشخص به‌عنوان نامطمئن علامت‌گذاری می‌شوند و به‌عنوان ناپدید شدن یا بسته شدن تاییدشده تلقی نمی‌شوند: میزبان‌های دارای خطا در `uncertain_hosts` ظاهر می‌شوند و هر گذار پورتی که شامل `unknown` باشد (از جمله unknown در هر دو اسکن) به جای `port_changes` در `unconfirmed_ports` فهرست می‌شود، به جز پورتی که در اسکن بعدی open باشد که یک تغییر پورت محسوب می‌شود. `compare` و `diff` پورت‌ها را با یک قانون یکسان دسته‌بندی می‌کنند. `no_longer_responding` به معنای عدم پاسخ است، نه اثبات حذف شدن دستگاه. کد خروج 0 اسکن تضمین نمی‌کند که هر میزبان پاسخ داده باشد: خطاهای هر میزبان را بررسی کنید. موفقیت در مقایسه، چه تغییری وجود داشته باشد چه نه، کد 0 برمی‌گرداند؛ دستور `diff` فایلی موجود قرارداد کد خروج 3 خود را حفظ می‌کند. تاریخچه پشتیبانی‌نشده یا خراب کد 1 برمی‌گرداند.

تاریخچه اطلاعات فهرست موجودی را ذخیره می‌کند، بنابراین یک پوشه محلی با حفاظت مناسب انتخاب کنید. فایل‌های پروفایل و تنظیمات ذخیره‌شده حاوی اطلاعات احراز هویت SNMP نیستند؛ مدیریت اطلاعات احراز هویت همچنان از طریق گزینه‌ها و متغیرهای محیطی زمان اجرای موجود انجام می‌شود.

## مقایسه فهرست موجودی (diff)

```bash
hostcensus scan 10.0.0.0/24 -q --save-snapshot monday.json
hostcensus scan 10.0.0.0/24 -q --save-snapshot tuesday.json
hostcensus diff monday.json tuesday.json             # table
hostcensus diff monday.json tuesday.json -f json     # JSON on stdout
```

یک اسنپ‌شات JSON شامل `format: "hostcensus-snapshot"`، `version: 1`، نسخه hostcensus، زمان ایجاد به UTC، هدف، مقادیر `timeout` و `backend` اسکن در صورت ثبت شدن توسط اسکن، سرویس‌های کاوش‌شده و میزبان‌های زنده در همان قالب گزارش `-o` است. میزبان‌های خاموش حذف می‌شوند. `diff` همچنین گزارش‌های ساده JSON حاصل از `scan -o` را می‌پذیرد، از جمله گزارش‌هایی که پیش از وجود فیلد `services` تولید شده‌اند.

`diff` میزبان‌های جدید و ناپدیدشده، پورت‌هایی که روی میزبان‌های حاضر در هر دو اسکن باز یا بسته شده‌اند و سرویس‌هایی که `version` آن‌ها تغییر کرده را گزارش می‌دهد. پورت‌هایی که فقط در یکی از دو اسکن کاوش شده‌اند مقایسه نمی‌شوند و یک هشدار این موضوع را اعلام می‌کند. مشاهدات ناموفق هرگز به عنوان "بدون تغییر" خوانده نمی‌شوند: پورتی که در هر یک از دو اسکن `unknown` باشد و در اسکن بعدی باز نباشد، به جای `closed` در بخش `unconfirmed` فهرست می‌شود با `before` از نوع `open`، `unknown` یا `not-open` (کاوش‌شده و بسته یا فیلترشده) و `after` از نوع `unknown` یا `not-open`؛ پورتی که اکنون باز است زیر `opened` گزارش می‌شود حتی اگر کاوش قبلی شکست خورده باشد. میزبانی که تمام کاوش‌های آن در هر یک از دو اسکن بدون پاسخ شکست خورده باشند، به جای `vanished_hosts` در `unsettled_hosts` فهرست می‌شود (با `before`/`after` از نوع `up`، `uncertain` یا `absent`، از جمله زمانی که در هر دو اسکن شکست خورده یا در فایل دیگر وجود نداشته باشد)؛ اگر در اسکن بعدی پاسخ دهد، همچنین به‌عنوان میزبان جدید همراه با پورت‌های بازش گزارش می‌شود. اسنپ‌شات‌ها این میزبان‌های ناموفق را به همین دلیل نگه می‌دارند. همچنین هنگامی که اهداف متفاوت باشند و هنگامی که هر دو فایل timeout یا backend را ثبت کرده باشند و آن مقادیر تفاوت داشته باشند، هشداری ظاهر می‌شود. `-o PATH` شکل JSON را در یک فایل نیز می‌نویسد.

گزارش یک اسکن که با `--deadline` متوقف شده (`"complete": false`) فقط میزبان‌هایی را که به آن‌ها رسیده فهرست می‌کند، بنابراین `diff` و `export` آن را با کد خروج 2 رد می‌کنند. `--allow-partial` آن را با یک هشدار در stderr می‌پذیرد: سپس `diff` میزبان‌هایی را که اسکن ناقص اصلاً فهرست نکرده به جای ناپدیدشده، در `unsettled_hosts` به عنوان `unscanned` فهرست می‌کند (میزبانی که به عنوان خاموش فهرست کرده باشد همچنان ناپدیدشده است)، `partial` را روی true قرار می‌دهد و هرگز عدم تغییر را گزارش نمی‌دهد، و `export` هشداری در سرآیند اسکریپت می‌نویسد.

کدهای خروج `diff`: `0` بدون تغییر، `3` تغییرات یافت شد، مشاهداتی که قابل تایید نبودند یا ورودی ناقص (`changed` هرگاه هر فهرستی، از جمله `unsettled_hosts` و `unconfirmed`، غیرخالی باشد یا `partial` true باشد، مقدار true دارد)، `2` فایلی مفقود است، غیرقابل خواندن است، اسنپ‌شات پشتیبانی‌شده نیست یا بدون `--allow-partial` ناقص است، `1` فایل `-o` قابل نوشتن نبود.

## خروجی برای Kadupul

[Kadupul](https://github.com/kadupulhq/kadupul) (انشعابی از Cacti 1.2.31) قابلیت ورود انبوه دستگاه از فایل را ندارد. روش پشتیبانی‌شده آن برای افزودن دستگاه‌ها از طریق اسکریپت، `cli/add_device.php` است، یک دستگاه در هر فراخوانی، با آرگومان‌های `--option=value`. دستور `hostcensus export` یک اسکریپت POSIX `sh` از این فراخوانی‌ها می‌نویسد:

```bash
hostcensus scan 10.0.0.0/24 -q --save-snapshot inventory.json
hostcensus export inventory.json -o kadupul-import.sh --template 1
# or in one step, with template 0: hostcensus scan 10.0.0.0/24 -q -o kadupul-import.sh

# on the Kadupul server, as the user that owns the install:
export HOSTCENSUS_SNMP_COMMUNITY=...        # only if the script asks for it
KADUPUL_ROOT=/var/www/html/kadupul sh kadupul-import.sh
```

هر میزبان زنده تبدیل به `php "$KADUPUL_ROOT/cli/add_device.php" --description=... --ip=... --template=N ...` می‌شود:

- میزبان‌هایی که پرس‌وجوی SNMP اسکن برای آن‌ها موفق بوده `--version=2 --community=...` یا `--version=3 --username=... --authproto=... --password=...` (به‌علاوه `--privproto`/`--privpass` برای authPriv)، `--port` و `--avail=snmp` می‌گیرند. خروجی SNMPv3 نیازمند `--snmp-user` است و noAuthNoPriv رد می‌شود زیرا `add_device.php` برای v3 به گذرواژه نیاز دارد.
- سایر میزبان‌ها `--version=0 --avail=ping` دریافت می‌کنند، با `--ping_method=tcp --ping_port=` برابر با اولین پورت باز TCP، یا ICMP در صورت نبود پورت باز.
- `--notes` سرویس‌ها و نسخه‌های باز را فهرست می‌کند. `--description` نام DNS معکوس است وقتی ساده باشد (حروف، ارقام، `.`، `_`، `-`) و در غیر این صورت IP است، و یکتا ساخته می‌شود زیرا `add_device.php` با یک description تکراری به‌عنوان به‌روزرسانی آن دستگاه برخورد می‌کند.

هر مقدار اعتبارسنجی شده و با `shlex.quote` نقل‌قول می‌شود. به‌طور پیش‌فرض هیچ راز SNMP نوشته نمی‌شود: اسکریپت در زمان اجرا متغیرهای `HOSTCENSUS_SNMP_COMMUNITY`، `HOSTCENSUS_SNMP_AUTH_KEY` یا `HOSTCENSUS_SNMP_PRIV_KEY` را بسط می‌دهد و اگر یکی از آن‌ها تنظیم نشده باشد متوقف می‌شود. `--include-credentials` به جای این کار مقادیر را از آن متغیرهای محیطی در اسکریپت می‌نویسد، آن را با حالت 0600 می‌سازد و هشداری ثبت می‌کند. خود `add_device.php` مقدار community را چاپ می‌کند و اسرار را به‌عنوان آرگومان دریافت می‌کند که هنگام اجرای هر فراخوانی در فهرست پردازش‌های سرور Kadupul قابل مشاهده هستند.

`add_device.php` برای موارد تکراری و خطاها با کد 1 خارج می‌شود؛ اسکریپت ادامه می‌دهد، شکست‌ها را می‌شمارد و اگر هر دستگاهی اضافه نشده باشد با کد 1 خارج می‌شود. شناسه‌های الگو از `php cli/add_device.php --list-host-templates` به دست می‌آیند. کدهای خروج `export`: `0` نوشته شد، `2` ورودی غیرقابل خواندن، اسکن ناقص بدون `--allow-partial` یا داده‌هایی که نمی‌توان به‌صورت ایمن خروجی گرفت، `1` اسکریپت قابل نوشتن نبود.

## نسخه‌گذاری و فرآیند انتشار

hostcensus از [Semantic Versioning](https://semver.org/spec/v2.0.0.html) پیروی می‌کند: اصلاحات سازگار نسخه patch را افزایش می‌دهند، ویژگی‌ها و منسوخ‌سازی‌های سازگار نسخه minor را افزایش می‌دهند، و تغییرات ناسازگار نسخه major را افزایش می‌دهند. دستورات و گزینه‌ها، کدهای خروج و JSON Schemaها قرارداد عمومی هستند؛ رفتار منسوخ‌شده تا نسخه اصلی بعدی به کار خود ادامه می‌دهد، مگر اینکه یک اصلاح امنیتی تغییر زودتر آن را ایجاب کند (که در این صورت changelog دلیل آن را بیان می‌کند).

release-please یک PR انتشار را از روی عنوان‌های Conventional Commit در شاخه `main` باز می‌کند و `pyproject.toml`، `uv.lock` و `CHANGES.md` را به‌روزرسانی می‌کند. ادغام (merge) آن تگ `vMAJOR.MINOR.PATCH` و یک پیش‌نویس انتشار GitHub می‌سازد که CI به آن یک wheel آزمایش‌شده، توزیع منبع و checksumها را پیوست می‌کند؛ GitHub گواهی‌های ساخت (build attestations) آن فایل‌ها را از طریق API گواهی‌های خود ذخیره می‌کند. یک نگه‌دارنده پس از پیوست شدن فایل‌ها پیش‌نویس را بررسی و منتشر می‌کند. انتشارها هرگز جایگزین نمی‌شوند.

انتشار مورد اعتماد PyPI اختیاری است و به مالکیت پروژه، یک ناشر مورد اعتماد و محیط `pypi` نیاز دارد. این روش همان مصنوعات انتشار بررسی‌شده را بدون ساخت مجدد یا ذخیره توکن API منتشر می‌کند. انتشارهای تگ‌شده در این مخزن عمومی گواهی‌های مصنوع GitHub تولید می‌کنند؛ فورک‌های خصوصی به طرح پشتیبانی‌شده و تایید صریح نیاز دارند. برای راه‌اندازی، دستورات دقیق و تلاش‌های مجدد به [راهنمای کامل انتشار](../../../docs/releasing.md) مراجعه کنید.

## توسعه

```bash
uv sync --locked                 # runtime plus the default `dev` group
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run pytest --cov=hostcensus
uv build --no-build-isolation
uv run twine check --strict dist/*.whl dist/*.tar.gz
```

ابزارهای توسعه در گروه‌های وابستگی [PEP 735](https://peps.python.org/pep-0735/) در `pyproject.toml` (`dev`، `fuzz`، `build`) قرار دارند، بنابراین هرگز در فراداده بسته منتشرشده ظاهر نمی‌شوند. `uv.lock` تنها فایل قفل است؛ CI با `uv sync --locked` نصب می‌کند و وقتی فایل قفل قدیمی باشد شکست می‌خورد. مفسر را با `uv python`، mise (`mise exec python@3.14 -- uv sync --locked`) یا هر پایتون 3.12+ انتخاب کنید.

CI حداقل 90% پوشش آزمون بسته را اجبار می‌کند. آزمون‌های واحد شامل سرورهای loopback کنترل‌شده و موارد آفلاین پروفایل/تاریخچه/اعتبارسنج انتشار هستند؛ آزمایشگاه Compose شامل OpenSSH، MariaDB، nginx و net-snmp روی یک پل ایزوله اجرا می‌شود. آن را با `make test-integration` اجرا کنید. به [CONTRIBUTING.md](../../../CONTRIBUTING.md) و [ابزارهای انتشار](../../../scripts/README.md) مراجعه کنید.

کانتینر زمان اجرا با UID/GID 10001 بدون پوشه خانگی، بدون ورود پوسته و بدون pip اجرا می‌شود و می‌تواند در `/app/output` بنویسد. به آن کاربر دسترسی نوشتن در هر پوشه خروجی متصل‌شده (mounted) بدهید. این کانتینر به هیچ capability نیازی ندارد و با سیستم‌فایل ریشه فقط‌خواندنی کار می‌کند، بنابراین می‌تواند به‌صورت زیر اجرا شود:

```sh
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
  --tmpfs /tmp -v "$PWD/out:/app/output" IMAGE scan 192.0.2.0/28 -o /app/output/report.json
```

Nmap در این کانتینر از رفتار کشف TCP بدون دسترسی ممتاز خود استفاده می‌کند. CI ساخت ایمیج را در صورت گزارش هر آسیب‌پذیری قابل اصلاح HIGH یا CRITICAL توسط Trivy با شکست مواجه می‌کند.

## بررسی‌های زنجیره تامین

[OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/somethingwithproof/python-network-discovery-tool) روی شاخه main و به‌صورت هفتگی اجرا می‌شود، امتیاز واقعی خود را منتشر می‌کند و یافته‌ها را در اسکن کد GitHub بارگذاری می‌کند. Actionها و ایمیج‌های پایه کانتینر با هش‌های تغییرناپذیر پین شده‌اند؛ وابستگی‌های پایتون در `uv.lock` تفکیک شده‌اند. خطاهای Bandit باعث شکست CI می‌شوند و فازینگ محدودشده Atheris تجزیه‌گرهای SSH، MySQL، HTTP، گواهی و SNMPv3 BER را بدون دسترسی به شبکه می‌آزماید.

Scorecard همچنین فعالیت بازبینی تاریخی، تنوع مشارکت‌کنندگان و منشا انتشار را اندازه‌گیری می‌کند. آن امتیازها شواهد واقعی را منعکس می‌کنند؛ آن‌ها ادعایی مبنی بر برآورده شدن هر بررسی حاکمیتی یا انتشار تاریخی نیستند. به [SECURITY.md](../../../SECURITY.md) و [منشا انتشار](../../../docs/releasing.md) مراجعه کنید.

## بومی‌سازی

پیام‌های CLI و جدول‌های خلاصه/تفاوت ترمینال از 45 زبان و ناحیه (`en`، `de`، `es`، `fr`، `it`، `pt-BR`، `nl`، `ru`، `uk`، `ja`، `ko`، `zh-CN`، `zh-TW`، `ar`، `hi`، `pl`، `tr`، `sv`، `vi`، `id`، `af-ZA`، `am-ET`، `ar-EG`، `ar-MA`، `fr-MA`، `fr-SN`، `ha-NG`، `ig-NG`، `mg-MG`، `rw-RW`، `so-SO`، `sw-KE`، `xh-ZA`، `yo-NG`، `zu-ZA`، `bn`، `fa`، `he`، `mr`، `ta`، `te`، `th`، `ur`، `ms`، `fil`) بدون هیچ وابستگی زمان اجرای اضافی پشتیبانی می‌کنند. تفکیک زبان به ترتیب `--lang`، سپس `LC_ALL`، `LC_MESSAGES` و `LANG` را در نظر می‌گیرد و در نهایت به `en` برمی‌گردد. JSON Schemaها، ستون‌های CSV و اسکریپت‌های خروجی در تمام زبان‌ها بدون تغییر باقی می‌مانند.

```bash
hostcensus --lang de version
LANG=ja_JP.UTF-8 hostcensus scan 192.0.2.0/28
```
