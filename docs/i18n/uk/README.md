hostcensus є CLI-інструментом на Python для повторюваної інвентаризації сервісів у мережах, якими ви керуєте. Він фіксує, що саме надають пристрої, порівнює спостереження в часі та генерує сценарії імпорту для Kadupul. Типовий бекенд використовує сокети asyncio без прав root; опційне виявлення через Nmap дає змогу ідентифікувати хости поза налаштованими портами сервісів.

## Чому hostcensus

Разовий звіт про порти не пояснює, чи змінилося наступне спостереження, чи воно просто завершилося помилкою. hostcensus поєднує явні стани сервісів, обмежені перевірки, багаторазові профілі сканування та локальну історію. Оператори можуть повторювати ту саму область сканування, аналізувати помилки та відрізняти невизначені спостереження від підтверджених змін.

- **Дані про сервіси:** ідентифікація SSH, вітання MySQL, заголовки HTTP, спостереження за TLS-сертифікатами, а також виявлення SNMP або автентифіковані запити system-MIB.
- **Повторювана область сканування:** іменовані профілі TOML, адитивні виключення, налаштовувані сервіси, обмеження на кількість хостів і перевірок, а також обмежена кількість воркерів.
- **Перевірки перед генерацією трафіку:** локальна попередня перевірка (preflight) валідує цілі, інструменти, доступ до призначень, схему історії та налаштовані пакети кореневих сертифікатів TLS CA.
- **Історія інвентаризації:** транзакційні знімки SQLite зберігають усі спостереження; порівняння зберігають видимими збої сканера та невідомі стани.
- **Сумісний вивід:** вивід у термінал, звіти у форматах JSON і CSV, версіоновані файлові знімки та сценарії імпорту Kadupul.

CI охоплює Python 3.12, 3.13 і 3.14 на Linux та macOS, а також контрольовану інтеграційну лабораторію на базі Compose. Код використовує сучасні псевдоніми типів, типізовані результати preflight, слотові профілі з параметрами лише за ключовими словами та структуроване асинхронне очищення ресурсів, зберігаючи сумісність із цими версіями середовища виконання. Дивіться [керівництво з версіонування та релізів](../../../docs/releasing.md), щоб дізнатися про контракт сумісності SemVer і процес випуску релізів на GitHub. Значок релізу описує опубліковані артефакти, а не поточну копію репозиторію: останній опублікований тег наразі `v0.3.0`, тоді як ця копія використовує версію пакета `3.0.0`. Встановіть інструмент із цієї копії репозиторію, щоб користуватися описаними тут можливостями інвентаризації.

Почніть із розділу [встановлення](#install), а потім перейдіть до [профілів та історії](#inventory-profiles-preflight-and-local-history). Деталі інтеграції дивіться в розділах [відбитки сервісів](#fingerprints), [порівняння файлів](#inventory-diff) та [експорт до Kadupul](#kadupul-export).

## Встановлення

Потрібен Python 3.12 або новіший; матриця тестування охоплює Python 3.12–3.14. У цій копії репозиторію встановіть зафіксовані залежності середовища виконання:

```bash
uv sync --locked
uv run hostcensus --help
uv run hostcensus --version
uv run hostcensus preflight 127.0.0.1
uv run hostcensus scan 127.0.0.1 --services ssh -o loopback.json
```

Для опційного виявлення хостів за допомогою Nmap встановіть виконуваний файл Nmap через менеджер пакетів вашої платформи; додатковий пакет Python не потрібен. XML-вивід Nmap розбирається за допомогою defusedxml, основної залежності, тому розширення сутностей відхиляється. hostcensus запускає `nmap`, знайдений у `PATH`, напряму з фіксованим списком аргументів, крайнім терміном виконання, що зростає разом із розміром префікса, і лімітом виводу в 64 MiB. Для типового бекенду Nmap не потрібен.

## Міграція з netprobe

hostcensus це нова назва netprobe, випущена у версії 3.0.0. Проєкт ніколи не публікувався в PyPI під жодною з назв, тому встановлення виконувалися з копії репозиторію або з релізу на GitHub. Репозиторій GitHub зберігає свою початкову назву.

| Було | Стало | Сумісність |
| --- | --- | --- |
| Дистрибутив `netprobe` | `hostcensus` | Перевстановіть із копії репозиторію; пакета зі старою назвою немає. |
| Команда `netprobe` | `hostcensus` | `netprobe` усе ще працює та виводить одне попередження про застарілість у stderr. Коди завершення та stdout не змінилися. Буде видалено в наступному мажорному релізі. |
| Змінні середовища `NETPROBE_*` | `HOSTCENSUS_*` | Змінна `NETPROBE_*` використовується, якщо її аналог `HOSTCENSUS_*` не задано, з одним попередженням у stderr, яке називає імена змінних і ніколи не виводить їхні значення. Якщо задані обидві, пріоритет має `HOSTCENSUS_*`. Буде видалено в наступному мажорному релізі. |
| `import netprobe`, `python -m netprobe` | `import hostcensus`, `python -m hostcensus` | **Несумісна зміна.** Прокладка сумісності для імпортів не встановлюється; оновіть імпорти. |
| Тег Docker-образу `network-discovery:test` (лише CI) і користувач контейнера `netprobe` | `hostcensus:test`, користувач `hostcensus` | Жоден образ не публікувався в реєстрі. Перезберить образ і використовуйте точку входу `hostcensus`. |
| `netprobe.toml`, `netprobe-history.sqlite3` | `hostcensus.toml`, `hostcensus-history.sqlite3` | Наявний файл зі старою типовою назвою все ще використовується з попередженням, доки не існує файл із новою назвою. Явно задані шляхи `--config` і `--history` не зачіпаються. |
| Звіти та знімки з `"format": "netprobe-report"` або `"netprobe-snapshot"` і полем `netprobe_version` | `hostcensus-report`, `hostcensus-snapshot`, `hostcensus_version` | `diff` і `export` усе ще завантажують файли, записані під старою назвою, а опубліковані схеми JSON приймають обидва варіанти написання. Нові файли використовують нові назви. Бази даних історії SQLite не змінилися та завантажуються як і раніше. |
| Сценарії Kadupul із `netprobe export` | Сценарії з `hostcensus export` | Старі сценарії продовжують працювати та під час запуску все ще читають `NETPROBE_SNMP_*`. Нові сценарії читають `HOSTCENSUS_SNMP_*`. |

## Коди завершення

| Команда | 0 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| `scan` | спостереження або звіт записано | помилка preflight/бекенду, історії чи запису звіту або знімка | некоректна ціль, параметри, конфігурація або ліміти | - | досягнуто `--deadline`; частковий звіт записано, історію та знімок пропущено |
| `preflight` | перевірки пройдено | локальна перевірка завершилася помилкою | некоректна ціль/конфігурація або конфліктні призначення | - | - |
| `profiles` | перелік валідованих профілів виведено | - | нечитабельна або некоректна конфігурація чи вибір | - | - |
| `history` | зведення виведено | відсутня, некоректна або непідтримувана історія | некоректні параметри CLI | - | - |
| `compare` | порівняння сформовано, зокрема за наявності змін | нечитабельна історія, несумісна область або порядок, чи помилка запису | некоректні параметри CLI | - | - |
| `diff` | змін немає | не вдалося записати файл `-o` | відсутній, нечитабельний або непідтримуваний вхідний файл, або неповне сканування без `--allow-partial` | виявлено зміни, непідтверджені спостереження або неповне сканування | - |
| `export` | сценарій записано | не вдалося записати сценарій | нечитабельний вхідний файл, неповне сканування без `--allow-partial` або дані, які неможливо безпечно експортувати | - | - |

## Структура

| Модуль | Призначення |
| --- | --- |
| `cli.py` | Параметри команд, розв'язання профілів, preflight, сканування та формування звітів |
| `scanner.py`, `probes.py` | Розгортання цілей, обмежені воркери, виявлення хостів і спостереження за сервісами |
| `config.py`, `profiles.py` | Визначення сервісів і валідовані профілі інвентаризації |
| `models.py`, `output.py` | Типи результатів і формування виводу в термінал, JSON і CSV |
| `history.py`, `diff.py` | Історія SQLite і порівняння версіонованих файлових знімків |
| `preflight.py` | Локальні перевірки та обмежений запит версії Nmap |
| `export.py` | Валідовані та екрановані сценарії імпорту Kadupul |

Кожне спостереження за сервісом фіксує його стан окремо від оголошеної ідентичності. Читання та крайні терміни виконання обмежені; винятки перевірок залишаються в помилках хоста. Історія SQLite використовує транзакції, явне закриття з'єднань та шляхи лише для читання під час перегляду й порівняння. Секрети SNMP передаються лише через змінні середовища або файли секретів; історія інвентаризації зберігає фактичні несекретні налаштування. Детальніше про конвеєр сканування, його обмеження та межі довіри дивіться в [Архітектурі](../../../docs/architecture.md), а про авторизоване використання у [SECURITY.md](../../../SECURITY.md#authorized-use).

## Використання

Скануйте лише ті мережі, якими ви керуєте.

```bash
hostcensus scan 192.168.1.0/24              # table of alive hosts
hostcensus scan 192.168.1.1 -o results.json # JSON report
hostcensus scan 10.0.0.0/24 -o report.csv   # CSV report
hostcensus scan 10.0.0.0/24 -q -o out.json  # no table, file only
hostcensus scan 10.0.0.0/24 --format json | jq '.devices[]'  # JSON report on stdout
```

| Параметр | Значення |
| --- | --- |
| `NETWORK` | CIDR, IP або ім'я хоста; необов'язковий із `--profile`. Ідентифікатори області IPv6 відхиляються. |
| `-o, --output PATH` | Записати звіт у файл. Формат визначається за розширенням (`.json`, `.csv`); інші розширення використовують JSON за замовчуванням. |
| `-f, --format json\|csv\|kadupul\|auto` | Примусово задати формат звіту. Не діє без `--output`. `.sh` обирає `kadupul`. |
| `-v, --verbose` | Налагоджувальне журналювання. |
| `-q, --quiet` | Приховати результати, індикатор прогресу та інформаційні повідомлення; попередження й помилки все одно виводяться в stderr. |
| `--backend asyncio\|nmap` | Спосіб виявлення хостів. `asyncio` (типово) перевіряє порти сервісів напряму; `nmap` спочатку виконує ping-сканування через nmap і потребує виконуваний файл `nmap` у `PATH`. |
| `--timeout SECONDS` | Час очікування для перевірок, які не задають власний бюджет часу (типово 1.0). Вбудовані перевірки підключення використовують 0.3 с, якщо таблиця сервісів не задає `timeout`. |
| `--concurrency N` | Кількість одночасних перевірок у процесі виконання (типово 256). |
| `--deadline SECONDS` | Зупинити все сканування, включно з обходом nmap, після завершення цього часу (типово 3600, щонайбільше 604800; змінна середовища `HOSTCENSUS_DEADLINE`). Завершені хости записуються у звіт із `"complete": false`, історія та знімок не створюються, а `scan` завершується з кодом 4. |
| `--config PATH` | Файл TOML із визначеннями сервісів і необов'язковими іменованими налаштуваннями `[profiles]`. |
| `--profile NAME` | Використовувати іменований профіль; типово береться `hostcensus.toml`, якщо `--config` не вказано. |
| `--exclude IP/CIDR` | Додати виключення; можна повторювати за потреби. Виключений хост IPv4 також виключає адреси IPv6, що ведуть до нього: IPv4-відображені (`::ffff:a.b.c.d`), NAT64 (`64:ff9b::/96`) і 6to4. IPv4-відображені цілі та виключення трактуються як відповідні адреси IPv4. |
| `--max-hosts N` | Ліміт адрес, що перевіряється перед застосуванням виключень (типовий і жорсткий максимум 65 536). |
| `--history PATH` | Записати завершене сканування в опційну базу даних історії SQLite. |
| `--services NAMES` | Список назв сервісів через кому для перевірки в указаному порядку (типово: усі). |
| `--ports SPEC` | Список через кому у форматі `NAME=PORT` (перенести сервіс) або `PORT` (додати просту TCP-перевірку з назвою `tcp-PORT`). |
| `--snmp-community-file PATH` | Файл зі значенням community для SNMPv2c у запиті system MIB. Змінні середовища: `HOSTCENSUS_SNMP_COMMUNITY` (значення) або `HOSTCENSUS_SNMP_COMMUNITY_FILE` (шлях). |
| `--snmp-user` | Користувач SNMPv3. Змінна середовища: `HOSTCENSUS_SNMP_USER`. |
| `--snmp-auth-protocol`, `--snmp-auth-key-file PATH` | `MD5`, `SHA` (типово), `SHA224`, `SHA256`, `SHA384`, `SHA512` і файл із парольною фразою. Змінні середовища: `HOSTCENSUS_SNMP_AUTH_PROTOCOL`, `HOSTCENSUS_SNMP_AUTH_KEY` або `HOSTCENSUS_SNMP_AUTH_KEY_FILE`. |
| `--snmp-priv-protocol`, `--snmp-priv-key-file PATH` | `DES`, `AES` (типово), `AES128`, `AES192`, `AES192C`, `AES256`, `AES256C` і файл із парольною фразою. Змінні середовища: `HOSTCENSUS_SNMP_PRIV_PROTOCOL`, `HOSTCENSUS_SNMP_PRIV_KEY` або `HOSTCENSUS_SNMP_PRIV_KEY_FILE`. |
| `--save-snapshot PATH` | Додатково записати версіонований знімок для `hostcensus diff`. |
| `--tls-ca-file PATH` | Перевіряти сертифікати HTTPS за цим пакетом PEM замість системного сховища. Змінна середовища: `HOSTCENSUS_TLS_CA_FILE`. |

Типово кожен хост перевіряється на наявність SSH (TCP 22), SNMP (UDP 161), MySQL (TCP 3306), HTTP (TCP 80) та HTTPS (TCP 443). TCP-порти перевіряються через повне встановлення з'єднання. SNMP перевіряється запитом виявлення рушія SNMPv3, на який будь-який агент SNMPv3 повинен відповідати без облікових даних; агенти, що підтримують лише v1/v2c, цією перевіркою не виявляються. Із бекендом asyncio хост вважається активним, якщо будь-яка перевірка отримує відповідь, зокрема відмову в з'єднанні, тому хост, який відкидає всі пакети перевірок, отримує `alive=false` та помилку "Host is down"; це не доводить, що він фізично вимкнений. Із `--backend nmap` активні хости визначає nmap (ICMP за прав root, інакше TCP 80/443).

<a name="fingerprints"></a>

### Відбитки сервісів

Кожен відкритий сервіс отримує відбиток за тими даними, які він надсилає до автентифікації. Жодна перевірка не виконує автентифікацію, окрім запиту SNMP, і лише тоді, коли ви надаєте облікові дані.

| Перевірка | Що зчитує | `version` | Ключі `details` |
| --- | --- | --- | --- |
| `ssh` | рядок ідентифікації RFC 4253 | програмне забезпечення, наприклад `OpenSSH_10.0` | `protocol`, `software`, `comments` |
| `mysql` | початкове рукостискання MySQL/MariaDB | версія сервера | `server_version`, `flavor`, `auth_plugin` або `error_code`/`error` |
| `http` | відповідь на `HEAD /` | заголовок `Server` | `status`, `server` |
| `https` | рукостискання TLS, сертифікат, `HEAD /` | заголовок `Server` | `tls_version`, `cert_verified`, `cert_verify_error`, `cert_subject`, `cert_issuer`, `cert_sans`, `cert_not_before`, `cert_not_after` (UTC ISO 8601), `cert_self_signed`, `status`, `server` |
| `snmp` | виявлення SNMPv3; з обліковими даними GET для sysDescr, sysObjectID, sysName | sysDescr | `engine_id`; з обліковими даними `snmp_version`, `sys_descr`, `sys_object_id`, `sys_name` або `snmp_error` |

Цільове ім'я хоста розв'язується один раз на хост, і кожна перевірка підключається до цієї адреси, яка записується в результатах як `address`; саме ім'я використовується лише для TLS SNI, перевірки сертифіката та заголовка HTTP `Host`. Ім'я, яке не вдається розв'язати, дає стани `unknown` і помилку `Cannot resolve`. Імена зворотного DNS зберігаються лише тоді, коли містять допустимі символи імені хоста, і одночасно виконується щонайбільше 16 пошуків. HTTPS використовує перевірку сертифіката та імені хоста за системним сховищем або `--tls-ca-file`. Сховище довіри завантажується один раз для сканування та повторно використовується для кожної HTTPS-перевірки. Час TCP-з'єднання та TLS-рукостискання вимірюється окремо, тож порт, який приймає з'єднання, але зависає на рукостисканні, позначається як `open` із `tls_error`, а не `filtered`. Якщо перевірка не пройдена, результат фіксує `cert_verified: false` і `cert_verify_error`; повторні спроби зі слабшими налаштуваннями або HTTP-запит не виконуються. Деталі сертифіката та заголовки HTTP збираються лише після успішної перевірки. Для сервісів із приватним центром сертифікації надайте відповідний пакет CA. Старіші звіти можуть містити поле `cert_read_unverified`, яке сучасні перевірки більше не формують.

Секрети SNMP зчитуються лише зі змінних середовища або з файлів (`--snmp-*-file` чи відповідна змінна `HOSTCENSUS_SNMP_*_FILE`), але ніколи зі значень у командному рядку, які інші локальні користувачі можуть побачити у списку процесів. Передача значення у `--snmp-community`, `--snmp-auth-key` і `--snmp-priv-key` завершується з кодом 2 та вказує заміну. Файл секрету має містити непорожній текст UTF-8 розміром щонайбільше 4096 байтів; один завершальний символ нового рядка ігнорується, а одночасне задання змінної та файлу для одного й того самого секрету є помилкою. Повідомлення про помилки називають файл, але ніколи не виводять його вміст. Звіти сканування та історія навмисно не містять значень облікових даних. Експортер має окремий явний параметр `--include-credentials`, описаний нижче. Параметр community обирає SNMPv2c; користувач обирає SNMPv3 з автентифікацією, якщо задано ключ автентифікації, і з конфіденційністю, якщо задано обидва ключі (`snmp_security_level` фіксує обраний рівень). hostcensus із кодом завершення 2 відмовляється поєднувати community з користувачем v3, використовувати ключ шифрування без ключа автентифікації або використовувати ключі без користувача, і ніколи не повторює невдалий запит v3 через v2c чи нижчий рівень безпеки. Агенти, що підтримують лише v1/v2c, ігнорують запит виявлення v3 без облікових даних, тому відображаються як відкриті лише тоді, коли надано community.

Текст банера зводиться до друкованих символів і обрізається до 256 символів перед збереженням або відображенням. Читання також обмежені: 4 KiB на рядок, 4 KiB для вітання MySQL, 16 KiB для заголовків HTTP. Ідентифікатор рушія SNMP довший за 32 октети обрізається перед збереженням. HTTP і HTTPS надсилають заголовок Host з адресою IPv6 у квадратних дужках і з портом, якщо порт не дорівнює 80 або 443. Комірки CSV, що починаються із символу запуску формули табличного процесора, отримують префікс, щоб комірка залишалася текстом.

### Обмеження

Один запуск приймає щонайбільше 65 536 адрес, 64 сервіси та 524 288 перевірок (кількість хостів помножена на кількість сервісів); більші запити завершуються з кодом 2 ще до надсилання будь-якого трафіку. `--concurrency` обмежено значенням 4096 сокетів. Кожна перевірка має жорсткий крайній термін виконання, що вчетверо перевищує її власний бюджет часу. Перевірки підключення (`tcp`, `ssh`, `mysql`, `http`) використовують 0.3 секунди, якщо для сервісу не задано `timeout`. SNMP і HTTPS використовують `--timeout` (типово 1.0), якщо власний бюджет не задано. Перевірка, що досягла крайнього терміну, позначається як `unknown` із повідомленням "probe timed out" у полі `errors`. Локальні помилки сокетів (наприклад, вичерпання файлових дескрипторів) також позначаються як `unknown` із записом помилки; вони ніколи не вважаються відфільтрованим портом або вимкненим хостом. Перед початком перевірок hostcensus піднімає м'який ліміт відкритих файлів до жорсткого ліміту, щоб умістити `--concurrency` плюс 64 дескриптори; якщо це неможливо, перевірка preflight `open files` завершується невдачею, і `scan` завершується з кодом 1 до надсилання трафіку. Виявлення через Nmap використовує таймаут хоста 30 секунд. Префікс передається в nmap у формі CIDR, і обхід завершується помилкою з кодом 1, якщо nmap повертає менше адрес, ніж отримав (наприклад, ім'я, яке не вдається розв'язати), замість того щоб позначати хости як вимкнені. Цільове ім'я хоста розв'язується один раз, і nmap отримує цю адресу, тож виявлення та перевірки звертаються до однієї й тієї самої машини. Повний префікс запускається як один процес nmap із крайнім терміном виконання підпроцесу 35 секунд на кожні 256 адрес, із округленням угору. Обходи з виключеннями використовують пакети по 256 хостів і крайній термін 35 секунд для кожного пакета. Створення воркерів обмежене незалежно від розміру діапазону. Зворотний DNS та розв'язання імен хостів мають окремий двосекундний крайній термін; виклик резолвера, який ніколи не повертається, залишається в окремому потоці, щоб не утримувати роботу hostcensus довше за ці ліміти. Одночасно виконується щонайбільше 16 запитів пошуку, і покинутий виклик утримує свій слот до завершення, тому кількість завислих потоків залишається обмеженою; якщо зависнуть усі 16, наступні пошуки ставатимуть у чергу на слот поза двосекундним крайнім терміном (який починається після звільнення слота), доки `--deadline` не зупинить сканування. `NetworkScanner`, використаний як бібліотека без параметра `deadline`, може чекати на такий слот нескінченно довго. Параметр `--deadline` (типово одна година) обмежує весь запуск поверх усіх перелічених лімітів.

### Налаштування сервісів

Сервіси можна змінювати за допомогою файлу TOML:

```toml
[services.ssh]          # same name as a built-in: replaces it
port = 2222
timeout = 0.5

[services.admin-ui]     # a new service, probed like HTTPS
port = 8443
probe = "https"
```

`probe` має одне зі значень `tcp`, `ssh`, `mysql`, `http`, `https` або `snmp` і типово збігається з назвою сервісу, якщо вона є типом перевірки, інакше дорівнює `tcp`. Лише `snmp` використовує UDP. Назви сервісів складаються з малих літер, цифр, `-` та `_`. Два сервіси не можуть використовувати один і той самий порт і протокол; історія фіксує один стан для такої пари. `timeout` є необов'язковим, задається в секундах і становить щонайменше 0.05. Перевірки типу підключення (`tcp`, `ssh`, `mysql`, `http`) типово мають 0.3 секунди. `snmp` та `https` використовують параметр сканування `--timeout`, якщо для сервісу не задано `timeout`. `--timeout` не замінює бюджет часу, який уже визначено для сервісу.

Звіти JSON є версіонованими документами (`"format": "hostcensus-report"`, `"version": 1`), що записують ціль, перевірені сервіси та налаштування поруч із `devices`; `--format json` без `-o` виводить звіт у stdout замість таблиці. Кожен вивід JSON має опубліковану схему; дивіться [вивід JSON](../../../docs/json-output.md). Пристрої зберігають початкові поля `ip`, `alive`, `ssh`, `snmp`, `mysql`, `hostname` та `errors` і додають список `services` із полями кожної перевірки: `name`, `port`, `protocol`, `state` (`open`, `closed`, `filtered` або `unknown`, якщо перевірка зазнала локального збою чи вичерпала крайній термін), `version` та `details`. Вивід CSV отримує кінцеві стовпці `services` і `versions` для відкритих сервісів. Булеві прапорці `ssh`, `snmp` і `mysql` відповідають сервісам із точно такими самими назвами.

<a name="inventory-profiles-preflight-and-local-history"></a>

## Профілі інвентаризації, попередня перевірка та локальна історія

Іменовані профілі використовують той самий файл TOML, що й наявні визначення `[services]`. Скопіюйте [hostcensus.example.toml](../../../hostcensus.example.toml) у `hostcensus.toml` і вкажіть мережі, якими ви керуєте:

```toml
[profiles.office]
network = "192.168.1.0/24"
exclusions = ["192.168.1.1"]
services = "ssh,http,https,mysql"
concurrency = 32
timeout = 1.0
max_hosts = 256
backend = "asyncio"
```

```bash
hostcensus profiles --config hostcensus.toml
hostcensus preflight --profile office --config hostcensus.toml
hostcensus scan --profile office --config hostcensus.toml -o report.json
```

`preflight` розв'язує параметри та профілі точно так само, як і `scan`, включно з `--concurrency` для перевірки ліміту відкритих файлів, тож успішне проходження `preflight` означає, що `scan` запуститься з тим самим планом.

Профілі приймають поля `network`, `exclusions`, `services`, `ports`, `backend`, `timeout`, `concurrency` та `max_hosts`. `services` і `ports` використовують звичний синтаксис списків через кому. Явні параметри CLI перевизначають налаштування профілю; повторні параметри `--exclude` додаються до виключень профілю. Явно вказана мережа разом із `--profile` повинна входити в область IP/CIDR цього профілю. Імена хостів усе ще підтримуються для прямих сканувань, але не можуть поєднуватися з виключеннями за IP. Ліміти хостів застосовуються до виключень; загальний ліміт перевірок усе одно діє після них. Виключені хости вилучаються як із перевірок сервісів, так і з опційного виявлення через Nmap.

Кожне сканування виконує локальні перевірки preflight перед генерацією цільового трафіку: ліміти цілей і перевірок, доступ до призначень, доступність опційного виконуваного файлу або обгортки Nmap, схему історії та налаштований пакет кореневих сертифікатів TLS CA. `preflight` виводить результат у JSON, не сканує цілі та не створює базу даних історії. Для перевірки доступу до місця призначення без зміни наявного вмісту він тимчасово створює сусідній файл. Типовий бекенд asyncio так само не потребує ані Nmap, ані прав root. Шляхи призначень повинні відрізнятися один від одного та від вхідної конфігурації, зокрема з урахуванням жорстких посилань; символічні посилання в призначеннях відхиляються. Невдалі перевірки повертають код 1; некоректна область або конфігурація повертає код 2.

Запис звітів та експортних файлів вимагає підтримки `O_NOFOLLOW`. На платформах без неї, зокрема на Windows, такий запис завершується помилкою без відкриття чи обрізання файлу призначення. Нові звіти та сценарії експорту створюються з доступом лише для власника (режим 0600); заміна наявного файлу зберігає його права доступу. Запис в іменований канал без читача завершується помилкою негайно замість очікування. Нова база даних `--history` також створюється з доступом лише для власника; наявна зберігає свій режим доступу. Повідомлення журналу завжди спрямовуються в stderr, тому stdout містить лише результати. Експорти, що містять облікові дані, завжди примусово встановлюють режим 0600.

Історія вмикається за бажанням і доповнює наявні знімки JSON та команду `diff`:

```bash
mkdir -p output
hostcensus scan --profile office --history output/inventory.sqlite3
# Repeat later with the same targets and service selection.
hostcensus scan --profile office --history output/inventory.sqlite3
hostcensus history --history output/inventory.sqlite3 --limit 20
hostcensus compare 1 2 --history output/inventory.sqlite3
hostcensus compare 1 2 --history output/inventory.sqlite3 -o output/changes.json
```

Використовуйте ідентифікатори з `history`; приклад передбачає нову базу даних. Знімки зберігаються транзакційно разом із часом початку та завершення в UTC, версією пакета, фактичними несекретними налаштуваннями, зведеннями та всіма спостереженнями за хостами й сервісами, включно з помилками для кожного хоста. Неповні спостереження за хостами зберігаються. Скасовані запуски не зберігаються. Наявні контракти для звітів, знімків, експорту та кодів завершення сканування залишаються незмінними.

`history` виводить зведення в JSON без зчитування всіх історичних даних пристроїв. `compare` зчитує два збережені сканування, вимагає однакових ідентифікаторів цілей та вибраних портів і повідомляє про зміни доступності, статусу та станів портів. Ідентифікатор ранішого сканування повинен передувати ідентифікатору пізнішого. Якщо в обох скануваннях записано `timeout` або `backend` і ці значення різняться, звіт додає попередження, але все одно порівнює спостереження. Інший час очікування може призвести до того, що відфільтрований порт виглядатиме відкритим. Помилки сканера та невідомі стани портів позначаються як невизначені, а не як підтверджене зникнення чи закриття: хости з помилками потрапляють у `uncertain_hosts`, і кожен перехід порту за участю `unknown` (включно з `unknown` в обох скануваннях) наводиться в `unconfirmed_ports` замість `port_changes`, окрім випадку, коли порт відкритий у пізнішому скануванні (тоді це зміна порту). `compare` і `diff` класифікують порти за тим самим правилом. `no_longer_responding` означає відсутність відповіді, а не доказ видалення пристрою. Код завершення сканування 0 не гарантує, що відповів кожен хост: перевіряйте помилки для кожного хоста. Успішне порівняння повертає 0 незалежно від того, чи є зміни; файловий `diff` зберігає свій контракт із кодом завершення 3. Непідтримувана або пошкоджена історія повертає 1.

Історія зберігає відомості про інвентаризацію, тому обирайте належно захищений локальний каталог. Файли профілів і збережені налаштування не містять облікових даних SNMP; робота з обліковими даними й надалі відбувається через наявні параметри часу виконання та змінні середовища.

<a name="inventory-diff"></a>

## Порівняння інвентаризації

```bash
hostcensus scan 10.0.0.0/24 -q --save-snapshot monday.json
hostcensus scan 10.0.0.0/24 -q --save-snapshot tuesday.json
hostcensus diff monday.json tuesday.json             # table
hostcensus diff monday.json tuesday.json -f json     # JSON on stdout
```

Знімок має формат JSON із полями `format: "hostcensus-snapshot"`, `version: 1`, версією hostcensus, часом створення в UTC, ціллю, параметрами сканування `timeout` і `backend` (якщо сканування їх зафіксувало), перевіреними сервісами та активними хостами в тому самому вигляді, що й у звіті `-o`. Недоступні хости не включаються. `diff` також приймає звичайні JSON-звіти `scan -o`, зокрема створені ще до появи поля `services`.

`diff` повідомляє про нові та зниклі хости, порти, які відкрилися або закрилися на хостах, присутніх в обох знімках, і сервіси, у яких змінилося значення `version`. Порти, перевірені лише в одному з двох сканувань, не порівнюються, про що з'являється попередження. Невдалі спостереження ніколи не трактуються як "без змін": порт зі станом `unknown` у будь-якому зі сканувань, який не є відкритим у пізнішому, потрапляє до `unconfirmed`, а не `closed`, зі значенням `before` як `open`, `unknown` або `not-open` (перевірено і закрито чи відфільтровано) та `after` як `unknown` або `not-open`; порт, який зараз відкритий, потрапляє до `opened`, навіть якщо попередня перевірка зазнала збою. Хост, усі перевірки якого зазнали збою без відповіді в будь-якому зі сканувань, потрапляє до `unsettled_hosts` (зі значеннями `before`/`after` як `up`, `uncertain` або `absent`, зокрема коли він зазнав збою в обох скануваннях або відсутній в іншому файлі) замість `vanished_hosts`; якщо він відповідає в пізнішому скануванні, він також повідомляється як новий хост зі своїми відкритими портами. Саме з цієї причини знімки зберігають такі хости зі збоями. Попередження також з'являється, коли різняться цілі або коли обидва файли зафіксували таймаут чи бекенд і ці значення відрізняються. `-o PATH` також записує JSON-результат у файл.

Звіт зі сканування, зупиненого за `--deadline` (`"complete": false`), містить лише ті хости, до яких устиг дійти сканер, тому `diff` та `export` відхиляють його з кодом завершення 2. Прапорець `--allow-partial` дозволяє обробити його з попередженням у stderr: тоді `diff` записує хости, яких неповне сканування взагалі не перелічило, у `unsettled_hosts` зі станом `unscanned` замість зниклих (хост, зазначений як недоступний, усе одно вважається зниклим), встановлює `partial` у значення true і ніколи не повідомляє про відсутність змін, а `export` додає попередження в заголовок сценарію.

Коди завершення `diff`: `0` змін немає, `3` знайдено зміни, спостереження, які не вдалося підтвердити, або неповні вхідні дані (`changed` дорівнює true щоразу, коли будь-який список, включно з `unsettled_hosts` і `unconfirmed`, є непорожнім або `partial` дорівнює true), `2` файл відсутній, нечитабельний, не є підтримуваним знімком або є неповним без `--allow-partial`, `1` не вдалося записати файл `-o`.

<a name="kadupul-export"></a>

## Експорт до Kadupul

[Kadupul](https://github.com/kadupulhq/kadupul) (форк Cacti 1.2.31) не має пакетного імпорту пристроїв із файлу. Підтримуваний спосіб додавання пристроїв зі сценарію полягає у виклику `cli/add_device.php` по одному пристрою за виклик з аргументами `--option=value`. `hostcensus export` створює POSIX-сценарій `sh` із таких викликів:

```bash
hostcensus scan 10.0.0.0/24 -q --save-snapshot inventory.json
hostcensus export inventory.json -o kadupul-import.sh --template 1
# or in one step, with template 0: hostcensus scan 10.0.0.0/24 -q -o kadupul-import.sh

# on the Kadupul server, as the user that owns the install:
export HOSTCENSUS_SNMP_COMMUNITY=...        # only if the script asks for it
KADUPUL_ROOT=/var/www/html/kadupul sh kadupul-import.sh
```

Кожен активний хост перетворюється на `php "$KADUPUL_ROOT/cli/add_device.php" --description=... --ip=... --template=N ...`:

- Хости, для яких запит SNMP під час сканування завершився успішно, отримують `--version=2 --community=...` або `--version=3 --username=... --authproto=... --password=...` (плюс `--privproto`/`--privpass` для authPriv), `--port` і `--avail=snmp`. Експорт SNMPv3 потребує `--snmp-user`, а рівень noAuthNoPriv відхиляється, оскільки `add_device.php` вимагає пароль v3.
- Інші хости отримують `--version=0 --avail=ping` із `--ping_method=tcp --ping_port=`, де вказано перший відкритий TCP-порт, або ICMP, якщо таких портів немає.
- `--notes` перелічує відкриті сервіси та їхні версії. `--description` береться з імені зворотного DNS, якщо воно просте (літери, цифри, `.`, `_`, `-`), інакше використовується IP-адреса; опис робиться унікальним, оскільки `add_device.php` трактує наявний опис як оновлення відповідного пристрою.

Кожне значення перевіряється та екранується для оболонки за допомогою `shlex.quote`. Типово жоден секрет SNMP не записується: сценарій розгортає змінні `HOSTCENSUS_SNMP_COMMUNITY`, `HOSTCENSUS_SNMP_AUTH_KEY` або `HOSTCENSUS_SNMP_PRIV_KEY` під час запуску й зупиняється, якщо котрась із них не задана. Параметр `--include-credentials` натомість записує значення з цих змінних середовища у сценарій, створює його з режимом доступу 0600 і записує попередження в журнал. Сам `add_device.php` виводить community та приймає секрети як аргументи, які видно у списку процесів сервера Kadupul під час виконання кожного виклику.

`add_device.php` завершується з кодом 1 у разі дублікатів і помилок; сценарій продовжує роботу, підраховує збої та завершується з кодом 1, якщо бодай один пристрій не було додано. Ідентифікатори шаблонів можна отримати через `php cli/add_device.php --list-host-templates`. Коди завершення `export`: `0` записано, `2` нечитабельний вхідний файл, неповне сканування без `--allow-partial` або дані, які неможливо безпечно експортувати, `1` не вдалося записати сценарій.

## Версіонування та процес випуску релізів

hostcensus дотримується [Семантичного версіонування](https://semver.org/spec/v2.0.0.html): сумісні виправлення збільшують патч-версію, сумісні нові можливості та оголошення застарілості збільшують мінорну версію, а зміни, що порушують сумісність, збільшують мажорну версію. Команди та параметри, коди завершення й схеми JSON становлять публічний контракт; застаріла поведінка продовжує працювати до наступного мажорного релізу, якщо тільки виправлення безпеки не вимагає змінити її раніше (тоді в журналі змін пояснюється причина).

release-please відкриває PR для релізу на основі заголовків Conventional Commit у гілці `main`, оновлюючи версії в `pyproject.toml`, `uv.lock` і `CHANGES.md`. Злиття цього PR створює тег `vMAJOR.MINOR.PATCH` і чернетку релізу на GitHub, до якої CI додає протестований wheel, архів вихідного коду та контрольні суми; GitHub зберігає атестації збірки для цих файлів через свій API атестацій. Супроводжувач перевіряє та публікує чернетку після прикріплення файлів. Релізи ніколи не перезаписуються.

Надійна публікація в PyPI (trusted publishing) вмикається окремо та потребує володіння проєктом, налаштованого довіреного видавця і середовища `pypi`. Вона публікує ті самі перевірені артефакти релізу без повторної збірки чи зберігання API-токена. Теговані релізи в цьому публічному репозиторії генерують атестації артефактів GitHub; приватні форки потребують підтримуваного тарифного плану та явного ввімкнення. Інструкції з налаштування, точні команди та порядок повторних спроб дивіться в [повному керівництві з релізів](../../../docs/releasing.md).

## Розробка

```bash
uv sync --locked                 # runtime plus the default `dev` group
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run pytest --cov=hostcensus
uv build --no-build-isolation
uv run twine check --strict dist/*.whl dist/*.tar.gz
```

Інструменти розробки розміщені в групах залежностей [PEP 735](https://peps.python.org/pep-0735/) у файлі `pyproject.toml` (`dev`, `fuzz`, `build`), тому вони ніколи не потрапляють до метаданих опублікованого пакета. `uv.lock` є єдиним lock-файлом; CI виконує встановлення командою `uv sync --locked` і завершується помилкою, якщо lock-файл застарів. Оберіть інтерпретатор за допомогою `uv python`, mise (`mise exec python@3.14 -- uv sync --locked`) або будь-якого Python 3.12+.

CI забезпечує мінімальний поріг покриття коду тестами на рівні 90% для пакета. Модульні тести охоплюють контрольовані сервери на loopback та автономні сценарії для профілів, історії й валідатора релізів; лабораторія Compose запускає OpenSSH, MariaDB, nginx і net-snmp в ізольованій мережі bridge. Запускайте її командою `make test-integration`. Дивіться також [CONTRIBUTING.md](../../../CONTRIBUTING.md) і [інструменти релізу](../../../scripts/README.md).

Контейнер середовища виконання працює від імені UID/GID 10001 без домашнього каталогу, без інтерактивного входу в оболонку та без pip і може записувати в `/app/output`. Надайте цьому користувачу право запису до будь-якого змонтованого каталогу виводу. Контейнер не потребує додаткових привілеїв і працює з кореневою файловою системою лише для читання, тож його можна запускати так:

```sh
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
  --tmpfs /tmp -v "$PWD/out:/app/output" IMAGE scan 192.0.2.0/28 -o /app/output/report.json
```

У цьому контейнері Nmap використовує свою непривілейовану поведінку виявлення через TCP. CI зупиняє збірку образу в разі виявлення будь-якої вразливості рівня HIGH або CRITICAL, яку можна виправити, за звітом Trivy.
